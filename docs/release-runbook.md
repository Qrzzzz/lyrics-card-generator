# 标准发布入口

后续常规发布统一使用 `scripts/release.ps1`。已有 `release.yml` 继续负责
构建、安装测试、附件下载核验和公开发布；入口不降低现有门禁，也不在本地
重复下载安装包。模型只处理准备工作、失败诊断和最终结果汇报。

## 使用方式

### 发布候选准备

界面、文案或交互契约变化时，同步检查受影响的行为测试，例如窗口最小尺寸、
紧凑布局顺序、提示展示位置、焦点和选区恢复。开发完成前运行相关独立场景，
记录命令、提交与结果；完整回归继续由 CI 负责，不增加无条件本地全量门禁。
PR 提交前使用[准备清单](../.github/PULL_REQUEST_TEMPLATE.md)。标准发布入口
使用版本说明作为 PR 正文，因此 Agent 仍须遵守根目录 AGENTS.md 的准备要求。

首次失败后，先检查同一行为域的相邻断言、fixture 和等待条件，集中处理已知
问题再提交新候选。不得为通过测试而删除行为覆盖、放宽安全边界，或把尚未
完成的 Windows 原生高对比度、DPI、跨显示器验收描述成自动化已覆盖。

### 执行入口

在发布分支完成版本、六语言发布说明和相关修改并提交后执行：

```powershell
.\scripts\release.ps1 -Version 6.5.6 -CheckOnly
.\scripts\release.ps1 -Version 6.5.6 -Publish
# 终端中断或修复远端失败后，从原来的分支和提交恢复
.\scripts\release.ps1 -Version 6.5.6 -Resume
```

版本只是示例，应替换为实际版本。RC 使用 `6.5.6-rc.1`，包版本仍为
`6.5.6`。需要 Node.js、已安装的项目依赖、Git、已登录且具有发布权限的
GitHub CLI，以及 PowerShell。也可跨平台执行：

```text
node scripts/release-cli.mjs --version 6.5.6 --mode check
node scripts/release-cli.mjs --version 6.5.6 --mode publish
node scripts/release-cli.mjs --version 6.5.6 --mode resume
```

`CheckOnly` 默认启用，只检查版本、说明一致性、仓库配置及工作区，读取
GitHub 仓库信息，不推送、不创建 PR、不打标签。工作区不干净时退出码为 1，
明确列为阻塞；它不代表 CI 已通过或源码发布授权已通过。

`Publish` 表示授权完整的远端发布链：推送已准备的当前分支，创建或复用
PR，等待策略要求的检查，按精确 head SHA squash 合并，等待合并提交的
main CI，创建并推送 annotated tag，等待 Release 工作流，核对公开状态、
精确标签提交及四个附件的名称、大小、上传状态和 API SHA-256 摘要。
从 main 启动时，HEAD 必须已经对应唯一的已合并 PR。

不自动提交、不强推、不移动已有标签、不绕过审批或分支保护、不自动修复
测试，也不自动重跑失败工作流。新版本准备和代码审查仍是发布前工作。
Pages 有独立工作流；本入口确认桌面 Release，不声称已验证 Pages 部署。

## 等待、恢复与异常

- 每 60 秒查一次远端状态，阶段开始时输出提示，不持续打印完整日志。
  默认单次运行最多等待 90 分钟，可用 `-TimeoutMinutes 120` 调整；
  外部命令另有两分钟超时。超时不会撤销已完成的远端动作。
- 状态保存在 `git rev-parse --git-path release-state` 指向的 Git 元数据
  目录，按版本记录原始提交、分支、PR、合并提交、CI/Release run ID 和
  attempt、Release ID、附件摘要。该目录不进入提交。
- `Resume` 仍允许执行尚未完成的推送、合并、打标签步骤，属于发布授权。
  必须保留原始 checkout、提交及本地状态文件。它重新读取远端证据，不把
  本地完成标记当成跳过安全检查的依据。
- Windows 原子替换状态遇到 EPERM／EBUSY 时，入口最多短暂重试五次；其他错误立即传播。
  最终失败保留原正式状态及 tmp 供诊断，不删除正式文件或直接提升 tmp。恢复继续以正式
  状态和远端事实为准。即使日志显示标签推送成功，也使用 Resume 核验，不重复打标签。
- 失败时先查看输出中的 PR 或 run，读取对应失败步骤日志。修复需要更改
  源码时应走新的提交/发布准备流程，不修改旧状态文件去伪造匹配。
  远端瞬态失败可明确重跑原工作流，再 `Resume`。
- 先区分旧断言或 fixture、真实产品回归、测试时序和 runner/网络故障。
  诊断完成后优先显式重跑失败 job；GitHub 不允许该状态下重跑时，等待整轮
  结束后再执行，不重复提交相同请求。相关成功 job 不因排障再跑一次。
  同一失败重现后继续定位根因，不循环重跑直到变绿；一次重跑成功仅说明
  该次通过，偶发问题仍须保留 Issue 与失败证据。
- 标签推送后没有可见 Release run 时只等待和超时报错，避免重复构建。
  检查 Actions 后可显式执行
  `gh workflow run release.yml --ref v版本号 -f tag=v版本号`，
  再恢复；已经存在的标签不会重新创建或移动。
- 同版本并发执行由本地锁阻止。进程被强制终止留下锁时，确认没有运行中的
  发布进程后才删除错误消息指出的 `.lock` 文件，保留 `.json` 状态。

完整回归由 CI 执行，最终安装包验证由 Release 工作流执行。只有同一提交、
同一环境、相同检查契约的成功证据才能复用；PR 的 CI 不能替代 main 的
合并提交 CI。日志和状态只保存必要证据，不保存 GitHub token。

## 进度与耗时记录

操作人员或 Agent 汇报当前阶段、已耗时、已知阻塞、可用的 PR/run 链接和剩余
阶段。只有阶段变化、新失败、阻塞变化或用户询问时补充实质进展，避免重复
发送同一条等待消息。没有可靠依据时不承诺完成时间。

CLI 已增加等待阶段的开始/结束时间、阶段与本次调用累计耗时，并在远端状态变化时
输出 run URL、attempt 和缺失检查；失败指出 job/step。进度由同一进程查询。
状态新增 progress 和 phaseHistory，兼容旧 schema-1；累计时间指本次调用，
不把中断期间的时间伪装为脚本运行时间。

发布完成后记录端到端墙钟耗时、各阶段耗时、候选提交数、失败 job 与重跑
次数。并行 job 的时间不能相加后冒充用户等待时间；真实产品缺陷、测试缺陷
和 runner 故障分别记录。一次通过率按候选提交首次必需检查是否全部通过统计，
重跑后成功不计入首次通过；至少观察三次发布后再评价优化效果。

## 发布治理实施与后续观测

跟踪：[发布入口等待、进度与恢复诊断 #246](https://github.com/Qrzzzz/lyrics-card-generator/issues/246)。
桌面回归相关工作合并在 [#247](https://github.com/Qrzzzz/lyrics-card-generator/issues/247)，
不另建内容重叠的优化文档或重复 Issue。

2026-10-22 的 v6.8.1 发布入口从 16:43 到 19:06（Asia/Shanghai）约耗时
142 分钟，不含前期开发、原生验收和最后清理。涉及六轮 PR CI、两轮 main CI、
一轮 Release，另有三次桌面 job 重跑。最终 [main CI](https://github.com/Qrzzzz/lyrics-card-generator/actions/runs/39765198774)
约 13 分 29 秒，[Release](https://github.com/Qrzzzz/lyrics-card-generator/actions/runs/39766994640)
约 7 分 59 秒。PR/main/Release 的串行等待是现行授权链的成本；多轮测试修复
是本次额外耗时的主要来源。35–40 分钟仅为本次成功路径的粗估，25–30 分钟
是优化候选目标，均不是交付时限或硬编码 CI 性能门槛。

发布入口改进优先修改 `scripts/release-cli.mjs`，复用
`scripts/test-release-cli.mjs` 和现有 Git 元数据状态文件；不另建发布入口。

- [x] 新 PR 的检查尚未登记时，在有上限的登记等待期内继续等待，并输出原因；
  不把所有 CLI 非零退出都吞成等待。权限、认证、网络及格式错误明确报错。
- [x] 等待和恢复始终验证当前 PR head、check/run SHA 与 attempt；旧提交成功、
  缺失检查、失败、取消或跳过的必需检查不能授权合并或发布。
- [x] 输出阶段开始时间、累计耗时、run URL 和失败 job/step；进度只由发布进程
  统一查询，不引入另一个并行轮询进程，不记录凭证或用户数据。
- [x] 若持久化新增进度字段，旧状态兼容；恢复后重新读取远端证据，不凭本地
  完成标记跳过检查，也不重复创建 PR、合并、推送标签或触发 Release。
- [x] 为登记延迟、登记超时、认证失败、head 变化、缺失/失败检查、恢复与
  重复调用增加确定性用例；验证现有来源授权、工作流契约和 PowerShell 检查。

桌面回归的分组、制品共享和稳定性验收并入
[CI 门禁职责](./testing/ci-gates.md#桌面回归实施与观测)。上述勾选仅表示本地实现及确定性用例，
不表示远端 CI/发布验证或 Issue 已关闭。至少三次发布的耗时与首次通过率仍待观测。

PR 等待改用 Actions REST API：精确 PR head、CI workflow、关联 PR、当前 run attempt
及必需 jobs 一并验证。没有 run 或没有任何必需 job 时，登记等待最多 10 分钟；
已有必需 job 登记后的排队/运行继续受整次调用 deadline 约束。HTTP/网络/格式错误
直接失败，REST 单次请求另有两分钟超时；完成后缺失、跳过、取消或失败的必需检查
均不授权。主分支同样核对 jobs。

更新已有发布 PR 时，本次推送前观察到的旧 head 可能暂时仍由 API 返回。
入口在自己的推送成功后保存 PR 编号和待同步的旧／目标 SHA，最多等待两分钟；
只有这个已知旧 head 可以等待。出现第三个 SHA、仓库／分支／PR 状态变化或
API 错误立即停止，不把其他提交当作目标。同步状态兼容旧状态文件；等待中断后
Resume 重新读取 PR，继续精确 SHA 核验，不重复已登记的推送或创建 PR。
这段等待仍计入整次调用的总时限；超时后先核对 PR 与远端分支再恢复。

共享桌面回归目前仅通过手动 CI 输入 `desktop_shared_groups=true` 试运行。失败时先读
分组证据，再显式重跑失败 job；同一 run 中未重跑的成功分组，只能与相同 SHA、构建
摘要和契约一起复用。构建制品过期须重建并重跑全部消费组；不复用旧 SHA 的结果。
默认 PR/main 继续旧串行执行路径，稳定必需检查名保持 `desktop-packaged-regression`。

共享组在下载前以只读 Actions 权限核对精确 artifact ID、源 run/SHA、构建 attempt、
有效期和摘要元数据，下载后仍执行内容及逐资源校验。404／410 可能表示缺失、到期或
不可访问，先检查源 run 和权限；认证、网络、格式错误单独报错，不自动重试或重建。
原制品确实不可用时，明确重新构建并执行全部三个消费组和聚合检查。新构建即使程序
字节相同，也有新的构建身份；不能只重跑原失败组并复用旧构建的其他成功结果。
